# LevelUp — Plan Doc

## TL;DR

After a team finishes the core taskset **and** the two always-on early-finisher
bonus tasks, surface a "**LevelUp**" offer: re-attempt the task they scored
*lowest* on, with a freshly-generated variant of the same task type and the
same learning objective. The team keeps the **max** of original vs. retry —
they can never lose points. Capped at **2** LevelUp attempts per session.

This pairs perfectly with the +2 always-on bonus shipped in #189:

- **Bonus tasks = breadth.** Same room, fresh content, different skill.
- **LevelUp = depth.** Same skill, fresh content, mastery on the one
  thing this team struggled with.

## Why

Currently, when a team finishes early, they get:

1. The core taskset.
2. +2 bonus tasks (new content, new task types).
3. Optionally, hidden quest tasks (Quest Mode only).

What's missing is a way for **leftover session time** to be reinvested in **the
specific concept the team got wrong**. Teachers consistently say "we should
have practiced X more" *after* a session. LevelUp lets the session itself
correct course in real time.

Pedagogically this aligns with:

- **Retrieval practice** — re-encountering the same idea spaced minutes apart.
- **Mastery learning** — the team owns the concept before moving on.
- **Formative re-assessment** — the standard classroom move: "try this one
  again, you've almost got it."

## UX

After bonus tasks are completed, on the LeaderboardScreen / NextTaskCard:

```
You've got time. Want to LevelUp?

🎯 Lowest score so far: Sequence — 6/10
   We'll regenerate a fresh version. Score stays the higher of the two.

  [ Yes, give me a fresh one ]    [ I'm done — final score this round ]
```

If accepted:

- The new task is injected at the top of that team's queue.
- The team sees a banner: "LevelUp — Sequence (re-attempt)".
- The original task in the report is annotated with `(upgraded)` and shows the
  **before → after** delta.

If declined, the team is done; their session ends normally.

## Triggers and gates

- **Available iff:**
  - The team has completed all `core` tasks (`requiredForCompletion === true`).
  - The team has completed both early-finisher `bonus` tasks
    (`requiredForCompletion === false`, generated by mainTasksetController).
  - The team has at least one non-zero, non-skipped task result.
  - The team has used fewer than `MAX_LEVEL_UP_ATTEMPTS = 2` LevelUps in this
    session.
  - Teacher hasn't disabled LevelUp for this session (per-session toggle).

- **Picks the LevelUp task by:**
  - Lowest `scorePercent` among completed-not-skipped tasks.
  - Tiebreak: most recent of the lowest (recency bias — students are more
    likely to want to fix something fresh in mind).
  - Eligibility: the task type must be in `LEVEL_UP_ELIGIBLE_TYPES` (see below).

## Eligibility — which task types can LevelUp?

Eligible (have a clean AI generator branch + objective scoring):

- multiple-choice, true-false, short-answer, cloze
- matching, sort, sequence, mad-dash-sequence
- timeline, vennsort
- spinner, trivia, riddle, brain-blitz, fake-out
- hangman-duel, mystery-clues
- flashcards, flashcards-race
- mind-mapper, brain-spark-notes
- pet-feeding, mad-dash
- tower-builder, hole-in-one
- musical-chairs, peer-editing
- legends, what-am-i

Ineligible (subjective / single-shot creative / coordination-based):

- open-text, letter, photo, photo-journal, draw, draw-mime, mime, role-play,
  role-play-deck, script-play, narration-synthesize, record-audio,
  collaboration, brainstorm-battle, echo-chain, team-selfie, mood-checkin,
  body-break, motion-mission, hide-and-seek, careers (multi-mode justification),
  current-events (live news already ran), interview, debate, ai-debate-judge

The list lives in `shared/taskTypes.js` as `TASK_TYPE_META[type].levelUpEligible`
so we don't have a parallel registry to forget.

## Scoring policy

- **Max scoring** — the team keeps `max(originalScore, retryScore)`.
  Never penalize trying again.
- The **retry counts in totals only once** (replaces the original line in the
  gradebook, doesn't double-count).
- Effort flag: if the retry score is higher than the original, the team earns a
  **+5 mastery bonus** (small enough to not distort, big enough to be a hook).
- If the retry is *lower*, the original score stands, no penalty, no mastery
  bonus.

## Server-authoritative content generation

LevelUp regenerates the task **on the server**, never client-side, so it
can't be probed for answers.

Path:

1. Client emits `student:requestLevelUp` with `{ roomCode, teamId, studentId }`.
2. Server picks the lowest eligible task → reads its `meta`, `learningObjective`,
   `gradeLevel`, `subject`.
3. Server calls `regenerateSingleTask(originalTask, { reason: 'level-up' })`
   in `sharedTasksetController.js` — same path overlays use, with a
   "different items than before" hint in the prompt.
4. Server validates the new task with `validateTaskByType` and sanitizes via
   the existing pipeline.
5. Server injects the variant as a new task in `room.taskset.tasks` with
   `isLevelUp: true`, `levelUpOfTaskId: <original task id>` markers.
6. Server emits `levelUp:taskReady` to that team's room only.
7. The team plays it. On submission, the scoring branch checks `isLevelUp` and
   computes the max-of-policy server-side.

## Data model additions

`student-app/src/store` — track per-team LevelUp attempts in memory.

`backend/models/TaskSet.js` (or equivalent room state):

```js
levelUpsByTeam: { type: mongoose.Schema.Types.Mixed, default: {} }
// shape: { teamId: { attempts: number, history: [{ originalTaskId, newTaskId, originalScore, retryScore }] } }
```

`shared/taskTypes.js` — extend TASK_TYPE_META with `levelUpEligible: true|false`.

`backend/index.js` — new socket: `student:requestLevelUp` + scoring branch
guard.

## Per-task annotation in reports

In the session report and emails:

- The original task line in the per-team breakdown shows `(upgraded)` after
  the title.
- A new column or footnote: `Original 6 → After LevelUp 9 (kept 9)`.
- The PDF gradebook uses the final (max) value; the trend column treats the
  improvement as legitimate growth.

If 0 teams used LevelUp in a session, the feature is silent in the report.
If ≥1 team used it, a small "LevelUp activity" block is added under the
existing overlay summary section showing per-team upgrades.

## Teacher controls

- **Per-session toggle** in LiveSession.jsx: "Allow LevelUp" (default ON).
- **Per-taskset default** in TaskSet schema: `levelUpEnabledByDefault` (default
  `true`).
- Teacher can also force-disable mid-session via `teacher:disableLevelUp`.

For graded assessments, teachers can turn it off so the score is a clean
one-shot signal.

## Tier gating

- LevelUp is available to **all tiers** (it's not gated behind PLUS/PRO).
- The +5 mastery bonus is universal.
- Per-student LevelUp history surfaces in the per-student progress portal
  (PRO) and in the gradebook (PLUS).

## Limits

- Max attempts: **2 per team per session**.
- Cooldown: ≥30 seconds between LevelUp attempts (so it's not spammed at
  end-of-session).
- No LevelUp during the final 60 seconds of teacher-set time (prevents
  half-finished retries).
- A given task type can be LevelUp'd at most once per session (so a team
  doesn't grind the same skill indefinitely).

## Edge cases

- **What if the team's lowest task is already a LevelUp result?**
  Skip to the next-lowest eligible original.
- **What if generation fails?**
  Show a friendly "couldn't generate a fresh one — try a bonus task instead"
  and don't deduct an attempt.
- **What if the team skipped the lowest task?**
  Skipped tasks (`score === 0` with skip flag) do **not** count as the lowest.
  We want the lowest *attempted* task.
- **What about Quest Mode hidden tasks?**
  LevelUp is offered AFTER bonus tasks and AFTER any hidden tasks are
  available, but a team can choose LevelUp instead of hidden. Hidden tasks are
  not eligible for LevelUp themselves (one-shot story content).
- **What if the team has multiple tasks tied for lowest?**
  Pick the most recent one (recency bias). UI shows the choice clearly.

## Testing checklist

- Generator produces a valid task of the same type with different items.
- Server rejects client-side LevelUp injection attempts (only socket-initiated
  flows are accepted).
- Scoring keeps the max correctly across original + retry.
- Report PDF shows the (upgraded) annotation and the delta line.
- Teacher toggle actually disables the offer.
- Attempt cap enforced server-side.
- Cooldown enforced server-side.
- Ineligible task types never appear as LevelUp candidates.

## Telemetry

Track in SessionAnalytics:

- `levelUpsOffered` (per team)
- `levelUpsAccepted` (per team)
- `levelUpsAccepted % offered` (acceptance rate, a UX signal)
- `meanImprovementPercent` (`retry - original`)
- `masteryBonusesAwarded` (how often retries beat originals)

This tells us whether the feature is actually helping students master
material, and where to tune.

## Open questions

1. Should LevelUp award the +5 mastery bonus even if the retry only ties the
   original (i.e., they got it right twice)? Current plan: NO, only on
   strict improvement. Re-evaluate after telemetry.
2. Should we surface the LevelUp option *during* the gradebook view at the
   end, after the team thinks they're done? Current plan: NO, only between
   tasks while there's clearly time. Could revisit if telemetry shows low
   acceptance.
3. Should we let students LevelUp a *teammate's* lowest task? Current plan:
   NO, simplicity. Could revisit for collaborative subjects.
